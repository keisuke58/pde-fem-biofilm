# クラウドから IKMHIWI03 へ（2026年10月13日）：並列でぶれる原因の確認ほか

短い作業だけ。長い計算は回さない（ユーザーの方針）。結果は `IKMHIWI03_TO_CLOUD.ja.md` に追記して push。

## 1. `-smp -np > 1` で結果がぶれる原因（最優先）

**背景。** `F:\biofilm_upf\ANSYS.exe`（8/19 の版）は `-smp -np > 1` で結果がぶれる（CLAUDE.md）。
別の実装で、同じ型の不具合が見つかった：USERMAT の**局所変数が静的に置かれ、全スレッドで共有される**
（gfortran の `-fno-automatic`、ifort の `/Qsave` や既定の静的割り当て）。各スレッドが同じ作業配列を
上書きし合うので、Gauss 点の応力や接線が混ざる。直し方は `RECURSIVE` を付けるか、`/auto`（ifort）で
局所変数をスタックに置くこと。

`link_v222.ps1` は `/auto` を付けている（`$switch` の行）。今の版（`F:\biofilm_upf_kusepy`、`_native`）が
並列で安全なのは、これで説明がつく可能性が高い。確かめたいのは次の 3 点。

1. **8/19 の版の作り方。** `F:\biofilm_upf` の exe を作ったときのコンパイルの記録（ANSCUST.BAT のログ、
   `.bat`、`*.log`）を探し、`/auto`、`/Qsave`、`/recursive` のどれが付いていたかを書く。見つからなければ
   「記録なし」と書く。
2. **局所変数を静的にしうる書き方。** Oliver の一式と私たちの追加分（`usermat_biofilm.f`、
   `usermat_py_hook.f`、`ecology_native.f`）で、次を grep して一覧にする：`SAVE` 文と `, save` 属性、
   `DATA` 文で初期化した局所変数、モジュール変数、USERMAT の中で**書き込まれる** COMMON。
   読むだけの定数（例：`usermat_biofilm.f` の `VI`、`VJ`、`MAP6`）は問題ない。書き込まれるものだけ挙げる。
3. **再現の確認（短い計算）。** 8³ の小さなデッキ 1 本（例：WP3 の 8³、T* = 0.1 程度、数分）を
   - `F:\biofilm_upf_kusepy` で `-smp -np 4` を 2 回、
   - `F:\biofilm_upf` で `-smp -np 4` を 2 回、
   回し、同じ設定の 2 回で応力（all_stress の SEQV）と α − 1 の最大差を書く。今の版が 1e−12 程度で一致し、
   8/19 の版がぶれれば、原因はほぼ確定。8/19 の版は使わないことを CLAUDE.md に明記する。

## 2. 境界の点の扱い（調べるだけ）

Oliver の要素で、境界の点の値を決める重みが**一次の当てはめ**かどうかを、ソース（Ussfin と NEM の
UserData）で確かめて書く。一次だと、境界近くのラプラシアンに O(1) の誤差が出て、拡散が速くなりうる。
直すのはまだ。修論の WP3 の誤差のうち、境界近くの分はクラウドで基準解から分けて見る。

## 3. 境界の値の更新の回数（調べるだけ）

境界の点の値（φ_b = Σ w_k φ_k）を、1 回の計算で済ませているか、収束するまで繰り返しているかを
ソースで確かめる。境界の点どうしが互いの値を使うので、1 回だけだと一定の場でも境界で一定にならない。
一定の場（φ = 0.5 一様、成長なし）を 1 ステップ回し、境界の点の φ が 0.5 からどれだけずれるかを書く
（ずれが 1e−12 を超えるなら 1 回だけの更新）。

## 4. NEM の演算子の自己テスト（できれば）

一次の場（u = x + 2y − z）と二次の場（u = x² + y z）を GP と境界の点に与え、NEM の勾配と
ラプラシアン（∇²u = 2）の誤差を、内部の GP と境界近くの GP で分けて書く。既存のデッキに APDL で
初期値を入れる形でよい。難しければ飛ばす。
